# Sales Photo Bot

Отдельный Telegram-бот, который превращает фотографию товара в карточку
продажи. Ручной справочник моделей не нужен.

## Как работает

1. Администратор публикует фотографию товара в заданном Telegram-канале.
   Исходная подпись, если она есть, переносится как `📞 Клиент: ...`.
2. Gemini Vision читает только разрешённые поля этикетки: код модели/SKU,
   память и цвет. Серийные номера, IMEI, штрихкоды, телефоны и QR исключаются.
3. Код/SKU ищется через Serper.dev — это отдельный B2B API обычной Google
   выдачи, а не встроенный Gemini Search Grounding. Название модели принимается
   только тогда, когда код и полное название встречаются минимум на двух
   независимых доменах. Сырые запросы, заголовки и сниппеты не сохраняются.
4. Бот сначала публикует копию фото по Telegram `file_id`. Только после
   успешной публикации и записи нового message ID он удаляет оригинал.
   Если ответ на `sendPhoto` потерялся из-за сетевого сбоя, операция намеренно
   не повторяется: Telegram мог уже принять публикацию, а бот не получает
   update на собственное сообщение канала. Оригинал остаётся на месте, возможную
   новую карточку нужно проверить вручную и затем снова загрузить фото.
5. Карточка содержит только уверенно распознанные поля. Если коммерческое
   название не подтверждено, строки `📦` нет; память и цвет могут остаться.
6. Кнопки `Olmas`, `Otabek`, `Ali`, `Abbos` добавляют менеджера и заменяются
   кнопкой `↩️ Назад`. Назад возвращает четыре кнопки.

Финансовый шаблон:

```text
🛒💵:
rasxod:

Наличка
💵:
🇺🇿:

Card/Terminal/Paynet
💵:
🇺🇿:
```

## Почему нужен именно канал

Сервис намеренно не запускается в группе/супергруппе. В группе сотрудники не
могут вручную редактировать сообщение, отправленное ботом, и поэтому не смогут
заполнить цену и `rasxod`. В канале администраторы с правом редактирования
публикаций могут заполнить эти поля.

Боту нужны права администратора канала:

- публикация сообщений;
- удаление сообщений.

Если `SALES_PHOTO_ALLOWED_USER_IDS` не задан, менеджерские кнопки доступны
только администраторам канала. Чтобы разрешить их конкретным не-администраторам,
укажите их Telegram user ID через запятую. Этот список дополняет, а не заменяет
администраторов канала.

## Секреты и переменные

Реальный `.env.sales-photo` не коммитится. Обязательны:

- `SALES_PHOTO_BOT_TOKEN` — новый отдельный token от BotFather;
- `SALES_PHOTO_CHAT_ID` — отрицательный ID канала;
- `GEMINI_API_KEY` — ключ Google AI Studio / Gemini Developer API;
- `SERPER_API_KEY` — ключ [Serper.dev](https://serper.dev/).

Полный безопасный шаблон находится в `.env.sales-photo.example`. Если token
когда-либо был отправлен в чат, лог или репозиторий, его нужно перевыпустить в
BotFather **до** выдачи админских прав и production-запуска.

При самом первом запуске бот очищает накопившиеся Telegram updates, чтобы не
удалить старые фотографии канала. Флаг первого запуска хранится в SQLite, поэтому
последующие обычные перезапуски очередь не очищают.

До запуска polling сервис проверяет Telegram-права, доступность выбранной Gemini
модели и ключ Serper. Проверка Serper выполняет один обычный поисковый запрос при
каждом старте процесса и расходует одну query из лимита.

## Проверка локально

```bash
python -m pip install -r requirements-sales-photo.txt
python -m unittest -q test_sales_photo_bot.py
```

Запуск без Docker:

```bash
set -a
source .env.sales-photo
set +a
python -m sales_photo_bot.main
```

## Docker и Coolify

Локальный Compose:

```bash
docker compose --env-file .env.sales-photo -f compose.sales-photo.yaml up -d --build
```

Для Coolify предпочтителен отдельный Compose resource на основе
`compose.sales-photo.yaml`:

- одна реплика;
- preview deployments выключены;
- stop-first deployment / Consistent Container Names, чтобы два polling-процесса
  одного Telegram token никогда не работали одновременно;
- persistent Docker volume `/app/data`;
- без домена и без публичного порта;
- runtime secrets, не build arguments;
- shutdown grace period не меньше 180 секунд.

Heartbeat экземпляра находится в `/tmp`, поэтому старый контейнер не может
сделать новый контейнер ложно healthy через общий volume. SQLite постоянно
хранит только технические message ID, состояние кнопки и краткий кеш
подтверждённого названия. Пока карточка ещё не опубликована, Telegram `file_id`
и короткая подпись клиента временно лежат в зашифрованном retry-payload; сразу
после фиксации новой карточки payload удаляется. Файл ключа
`sales_photo.db.key` находится в том же persistent volume, имеет режим `0600` и
должен резервироваться вместе с БД. Фото, сырые поисковые результаты и ответы
Gemini в БД не сохраняются.

Поколение менеджерских кнопок резервируется в SQLite до редактирования
Telegram-сообщения. Поэтому старый двойной клик не сможет перезаписать новый
выбор даже после рестарта. При редком сетевом сбое с неопределённым результатом
редактирования старые кнопки блокируются; такую карточку нужно проверить
вручную.

Docker healthcheck — это только локальная liveness-проверка maintenance loop.
Для production дополнительно нужен внешний alert по статусу контейнера: обычный
Docker Compose не перезапускает лишь потому, что контейнер стал `unhealthy`.

После первого запуска обязателен smoke-test: опубликовать известную коробку,
проверить карточку, удаление оригинала, четыре менеджерские кнопки и `Назад`,
затем вручную заполнить финансовые поля как администратор канала.
