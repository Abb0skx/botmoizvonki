# Sales Photo Bot

Отдельный Telegram-бот, который превращает фотографию, фотоальбом или коротко
написанную модель в карточку продажи. Изображения не скачиваются и не
анализируются: бот повторно использует готовые Telegram `file_id`. OCR, Gemini,
GPT, Google Search и другие внешние AI/API не используются.

## Как работает

1. Сотрудник публикует фотографию товара, Telegram-альбом или короткую модель в
   заданном канале. Из подписи или текста берутся один или два номера Узбекистана
   и приводятся к виду `+998 XX XXX XX XX`. Если отдельно указана дата вида
   `31/08`, она становится первой строкой `📆: 31/08/2026`. Год определяется по
   времени Ташкента как последний уже наступивший такой день, включая переход
   Нового года.
2. Каждая карточка получает строку `🆔: N`. Для каждого календарного дня по
   времени Ташкента своя последовательность начинается с `1`. Если сотрудник
   указывает прошлую дату, бот продолжает счётчик именно этой даты. Номер
   равен порядку оставшихся проданных товаров за этот день. Если одну карточку
   удалили, бот обнаруживает это при автоматической сверке и затем сдвигает все
   последующие ID этой даты без пропусков.
   Состояние хранится атомарно в SQLite и не сбрасывается после перезапуска.
3. Текст без фотографии обрабатывается только тогда, когда в нём есть модель:
   например, `A16 8/256`. Написанная модель переносится как есть, без поиска и
   угадывания. Сообщение, состоящее только из номера телефона, игнорируется.
4. Все фотографии одного `media_group_id` считаются одним товаром. Бот сохраняет
   весь альбом, поэтому фотография чека не теряется. Telegram не позволяет
   передать inline-кнопки прямо в `sendMediaGroup`, поэтому одна общая текстовая
   карточка с кнопками публикуется сразу под повторно отправленным альбомом.
5. Бот не загружает байты фотографий и не читает текст, штрихкоды, IMEI или S/N.
6. Бот сначала публикует копию фотографии по Telegram `file_id`, записывает ID
   новой карточки, выдерживает короткую защитную паузу и только затем удаляет
   оригинал. Если правка пришла до начала удаления, исправленный оригинал
   остаётся. Если удаление уже могло уйти в Telegram, бот сохраняет карточку-копию
   как страховку — обе фотографии одновременно не удаляются.
7. Кнопки `Olmas`, `Otabek`, `Ali`, `Abbos` фиксируют менеджера в базе и
   заменяются кнопкой `👤 Имя · ↩️ Назад`. Кнопка «Назад» возвращает четыре
   имени. Кнопки меняют только клавиатуру и поэтому не могут затереть вручную
   заполненные цену, `rasxod` или телефон.
8. После ручного редактирования карточки бот повторно проверяет строку
   `📞:` и нормализует в ней один или два номера. Одновременно нормализуются
   цены: последняя сумма в `🛒💵:` меньше `5000` получает `$`, большая
   или равная `5000` — `So'm`; суммы в точных строках `💵:` получают `$`, а
   суммы в `🇺🇿:` — разделители тысяч и жирный `So'm`. Комментарии после
   суммы, например `paynet Abbos`, сохраняются. `rasxod:` не изменяется. Если
   строку `🆔:` случайно удалили или изменили, бот восстанавливает сохранённый
   номер.
9. Автоисправление работает только с карточками, чья дата продажи — сегодня,
   вчера или позавчера по времени Ташкента. Более старая история не обходится.
   За один проход бот проверяет удаление карточки, существующую строку даты, ID,
   телефоны и цены; при правке сохраняет актуальную клавиатуру менеджера из базы.
   `rasxod`, модель, примечания и фотографии остаются без изменений.
   Неопубликованная карточка после ошибки
   отправки не занимает номер продажи: её резерв освобождается, опубликованные
   ID уплотняются, а успешный поздний retry получает следующий свободный номер.
10. Плановые проходы по времени Ташкента запускаются в `07:00`, каждый час с
    `10:00` до `18:00`, дополнительно в `18:30`, затем каждый час с `19:00` до
    `23:00`. Состояние расписания хранится в SQLite, поэтому после перезапуска
    выполняется один последний пропущенный проход текущего дня, а не все старые.
11. Каждая новая карточка также запускает отложенную проверку через пять минут.
    Если за эти пять минут появляется ещё одна модель, отсчёт начинается заново.
    Альбом считается одной моделью. Durable generation в SQLite не позволяет
    потерять или преждевременно завершить такой запуск при перезапуске либо при
    появлении новой модели во время проверки.
12. Telegram не присылает ботам отдельное событие ручного удаления сообщения.
    Автопроход читает актуальную карточку через тихую временную пересылку,
    немедленно удаляет её и исключает отсутствующий товар из дневного счётчика.
    Проверка начинается только по расписанию либо после пяти минут без новых
    моделей; вся история при этом не обходится.
13. Команда `/obnovit` в целевом канале запускает такую сверку вручную. Она также
    ищет среди недавних сообщений карточки, которые Telegram успел опубликовать,
    но чей успешный ответ потерялся из-за сетевой ошибки. Такая карточка
    восстанавливается по уникальному ID фотографии и участвует в пересчёте в
    фактическом порядке отправки товара.
14. После перезапуска бот сначала полностью принимает накопленные Telegram-правки
   и выдерживает защитное окно уже при работающем polling. Только после этого
   разрешаются повторные отправки и удаления из фоновой очереди.
15. Если база бота доставок подключена, карточка связывается с доставкой только
   при одном точном совпадении номера телефона и даты создания заказа по времени
   Ташкента. Одна доставка может связать несколько проданных товаров. Если для
   номера в тот же день найдено две или больше доставок, бот ничего не связывает
   и снимает прежнюю автоматическую связь.
16. Для однозначной доставки внизу появляются строки `Доставка:` и `Статус:`.
   Показывается фактический курьер и текущий статус; для завершённой доставки —
   реальное время `delivered_at`. Расчётное время прибытия не используется.
   Менеджер доставки выбирается автоматически только до ручного выбора в
   карточке. Ручной выбор или кнопка «Назад» всегда имеют приоритет.
17. С `11:00` до `21:00` каждый час бот отвечает служебным уведомлением на
   карточки за сегодня, вчера и позавчера, в которых пусто после `🛒💵:` или
   `📞:`, либо не выбран менеджер. Корректность телефона не проверяется —
   достаточно любого непробельного текста после двоеточия. В уведомлении всегда
   упоминается `@Texnikach_Admin`, перечисляются только незаполненные поля и,
   если он выбран, показывается имя менеджера. Перед новым уведомлением старое
   удаляется.
18. С `10:15` до `21:15` каждые 30 минут бот повторно проверяет заполненность и
   удаляет ставшее ненужным уведомление. Уведомления также удаляются, когда
   карточка удалена или вышла из трёхдневного окна проверки. Состояние хранится
   в SQLite, поэтому перезапуск не создаёт дубликаты.

Пример подписи:

```text
📆: 31/08/2026
🆔: 19

📦 A16 8/256

🛒💵:
rasxod:

📞: +998 90 123 45 67 / +998 91 765 43 21

Наличка
💵:
🇺🇿:

Card/Terminal/Paynet
💵:
🇺🇿:
```

## Почему используется канал

Сотрудники Telegram не могут вручную редактировать сообщение, отправленное ботом
в обычной группе. В канале администраторы могут дописать поставщика, цену,
`rasxod` и способы оплаты в опубликованную ботом карточку.

Боту нужны права администратора канала:

- публикация сообщений;
- удаление сообщений.

Каждому сотруднику, который вручную заполняет цену, `rasxod` и способы оплаты,
нужно выдать администраторское право Telegram «Изменение сообщений»
(`can_edit_messages`). Это право выдаётся сотрудникам, а не проверяется ботом.

Если `SALES_PHOTO_ALLOWED_USER_IDS` пуст, менеджерские кнопки доступны только
администраторам канала. Можно дополнительно перечислить Telegram user ID через
запятую.

## Настройка

Реальный `.env.sales-photo` не коммитится. Обязательны только:

- `SALES_PHOTO_BOT_TOKEN` — токен отдельного бота от BotFather;
- `SALES_PHOTO_CHAT_ID` — отрицательный ID канала.

Для связи с ботом доставок задаётся
`SALES_PHOTO_DELIVERY_DB_PATH=/app/delivery-data/delivery.db`. Обычные выборки
открываются только на чтение; узкий интеграционный мост изменяет только поля
очереди карточки продажи и `sync_needed`. Оба контейнера используют общий
volume под UID/GID `10001`. Синхронизация событий выполняется каждые
`SALES_PHOTO_DELIVERY_SYNC_SECONDS` секунд (по умолчанию `15`), а `/obnovit`
также вручную пересопоставляет карточки за сегодня, вчера и позавчера.

Шаблон находится в `.env.sales-photo.example`. Если токен попадал в переписку,
лог или репозиторий, его нужно перевыпустить в BotFather до production-запуска.

При первом запуске бот очищает накопившиеся Telegram updates, чтобы не обработать
старые публикации. Флаг первого запуска хранится в SQLite. В базе остаются только
технические ID сообщений, состояние кнопок и зашифрованный временный retry-payload.
Фото бот в SQLite не сохраняет.

## Проверка локально

```bash
python3 -m pip install -r requirements-sales-photo.txt
python3 -m unittest -q \
  test_sales_photo_bot.py test_sales_photo_phones.py \
  test_sales_photo_dates.py test_sales_photo_orders.py \
  test_sales_photo_prices.py test_sales_photo_auto_correction.py \
  test_sales_photo_delivery.py
```

Запуск без Docker:

```bash
set -a
source .env.sales-photo
set +a
SALES_PHOTO_DB_PATH="$PWD/sales_photo.db" python3 -m sales_photo_bot.main
```

## Docker

В Docker-образе нет Tesseract, ZXing и других OCR-компонентов.

```bash
docker compose --env-file .env.sales-photo -f compose.sales-photo.yaml up -d --build
```

Нужна ровно одна polling-реплика. Volume `/app/data` должен быть постоянным,
а deployment — stop-first, чтобы два процесса с одним Telegram-токеном не работали
одновременно. Compose также подключает существующий внешний volume
`texnikach-delivery-data`; бот продаж открывает саму SQLite-базу с `mode=ro`.
После запуска следует отправить тестовую фотографию, альбом и
короткую модель и проверить:

- отсутствие скачивания и обработки фотографии;
- одну карточку на весь альбом и сохранение всех его фотографий;
- игнорирование сообщения, состоящего только из телефона;
- создание текстовой карточки из короткой модели;
- нормализацию даты `DD/MM` в первую строку карточки;
- независимую ежедневную нумерацию и продолжение номера прошлой даты;
- автоматическое уплотнение ID после удаления товара;
- удаление оригинала только после появления карточки;
- четыре кнопки менеджеров и кнопку `Назад`;
- возможность администратора вручную заполнить финансовые поля;
- нормализацию одного и двух телефонов после ручного изменения подписи;
- нормализацию USD/UZS во всех ценовых строках с сохранением комментариев;
- ограничение автопрохода тремя последними датами продажи;
- плановые запуски по Ташкенту и перенос 5-минутного таймера новой моделью;
- однозначную связь по телефону и дате, связь одной доставки с несколькими
  товарами и отказ от связи при двух доставках;
- обновление курьера, статуса и фактического времени завершения без ETA;
- приоритет ручного менеджера над менеджером из доставки.
